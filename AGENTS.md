# AGENTS.md

FiscalCR: AI-powered, model-agnostic code review for GitHub pull requests. TypeScript (ESM), Node >= 20, pnpm (no `packageManager` pin at the root; the release workflow uses pnpm 9, `site/` pins pnpm 12.16.1). Shipped as a GitHub Action (`action.yml`) and a self-hosted GitHub App.

Agent navigation for this repo:

- [`.agents/AGENTS.md`](.agents/AGENTS.md) — router: which guide to read per task, source-of-truth hierarchy, non-negotiables.
- [`.agents/index.md`](.agents/index.md) — detailed, grep-friendly repo walkthrough (entry points, flows, testing map, change recipes).

## Layout

| Path | What |
| --- | --- |
| `src/` | The reviewer: `review/` (orchestrator), `pipeline/` (intent → group review → synthesis, fast path), `github/`, `config/`, `providers/` |
| `action/index.ts`, `action.yml` | The GitHub Action entry point and its public inputs |
| `test/unit/` | Vitest specs of current behaviour; `test/fixtures/` |
| `eval/` | Local LLM eval harness: 11 synthetic gold cases run through the real pipeline (guide: `docs/llm-evaluation.md`) |
| `site/` | Landing page: static Astro + Tailwind v4 on FTDS, its own `package.json`, deployed to GitHub Pages by `.github/workflows/site.yml` |
| `scripts/` | Prompt embedding, `llms.txt` generator, provider model sync, release helper |
| `PRODUCT.md`, `DESIGN.md` | Product and landing-page design context (owner-approved) |

## Commands

```sh
pnpm install
pnpm lint                 # tsc --noEmit (regenerates prompts first)
pnpm test                 # vitest run: test/**/*.test.ts and eval/**/*.test.ts
pnpm test grouper         # one file, by name filter
pnpm build                # dist/
pnpm build:action         # action/dist/ (ncc)
pnpm dev                  # the GitHub App in watch mode on :3000 (GET /health)
pnpm --dir site dev       # landing page on :4322
pnpm --dir site check-types
```

## Non-negotiables

- Keep both entry points working: GitHub Action (`action/index.ts`) and self-hosted GitHub App (`src/index.ts`).
- `src/config/schema.ts` (zod) is the canonical config definition; `src/config/defaults.ts` must mirror it.
- Run focused tests (`pnpm test`, vitest) for behavioral changes and keep `pnpm lint` (`tsc --noEmit`) green.
- Never commit `.env` (only `.env.example`), `.eval-results/`, or personal `.claude/` files (only `settings.json`, `launch.json`, `skills/`, `agents/` and `commands/` are shared).

## Generated files

- `action/dist/` — `pnpm build:action` (ncc). Gitignored; `release.yml` force-adds it to the release tag. Never hand-edit it.
- `src/pipeline/generated/` — `pnpm generate:prompts` (`scripts/embed-prompts.mjs`), run automatically by `lint`, `test`, `build` and `dev`. Edit the prompt sources, not the output.
- `llms.txt` (the setup guide for agents using FiscalCR) — `pnpm llms:sync`. Rerun it after changing `action.yml` or `src/config/`; `test/unit/llms.test.ts` checks it. `site/public/llms.txt` is regenerated by the site's `predev`/`prebuild`.
- Release-pinned provider models — edit `src/config/provider-models.ts`, then `pnpm models:sync` (see `.agents/subsystems/provider-models.md`).

## Checks

Nothing runs the checks automatically on a PR. There are no git hooks, and `.github/workflows/ci.yml` only runs FiscalCR's own review on the PR; type check and tests run only in `release.yml`, after a release is published. So run `pnpm lint` and `pnpm test` yourself before every commit (and `pnpm --dir site check-types` for site changes). If a hook or check is ever added, never skip it.

## Verifying changes

- **Reviewer behaviour** (pipeline, prompts, parsing, routing, providers): add or update a focused test in `test/unit/`, then `pnpm lint` and `pnpm test`.
- **Prompt or pipeline quality**: also run `make eval-llm-dry`. It is free (no key, no network) and prints routes, the provider-call bound and per-variant prompt sizes. Each case runs as *baseline* and *experimental* (the `experimental` config flag), so a prompt change made behind that flag can be compared against the current one.
- **Live eval** costs real provider calls and needs an API key (`API_KEY`, or `FISCALCR_API_KEY` / `ANTHROPIC_API_KEY` / `KIMI_API_KEY`) in a gitignored root `.env` or the shell. `make eval-llm` is the smoke run (6 calls), `make eval-llm-full` up to 40 calls; a decision run (`EVAL_RUNS=4 EVAL_MAX_CALLS=160 EVAL_SUITE=full make eval-llm`) up to 160. `EVAL_MAX_CALLS` caps spend before any call is made. Don't run a live eval unless the task asks for it or a key is already configured; never ask for a key in chat, print it or pass it on the command line. Results go to `.eval-results/`.
- **Action contract** (`action/index.ts`, `action.yml`): `pnpm build:action` must succeed; update README and rerun `pnpm llms:sync`.
- **Landing page** (`site/`): `pnpm --dir site check-types` and `pnpm --dir site build`, then look at it with the `site` entry in `.claude/launch.json` (:4322) in light and dark mode, at phone width and with the keyboard. Follow `DESIGN.md`.

## Git

Branches are `feat/<topic>`, `fix/<topic>` or `chore/<topic>`, merged to `main` by squashed PR. Commit subjects are Conventional Commits with an optional scope (`fix(site): …`), a plain sentence after the colon.

## Ask before changing

These add to the rules in `~/.claude/CLAUDE.md`:

- Action inputs and outputs (`action.yml`) and the repo config schema (`src/config/schema.ts`): users' workflows and `.fiscalcr-review.yml` files depend on them.
- The sticky-comment state marker format (`<!-- fiscalcr:state:v2 … -->`); a shape change needs a version bump and migration.
- Release-pinned provider models, and anything in `release.yml` or the tag-moving logic.
- `PRODUCT.md`, `DESIGN.md` and the landing page's look or copy.
